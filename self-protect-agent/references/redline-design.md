# 红线设计原则（Redline Design）

> 红线写得好不好，决定这个引擎是"真护栏"还是"安慰奶嘴"。
> 这一篇讲设计红线时的硬原则，避免三个常见死穴：靠自觉、靠黑名单、误报疲劳。

---

## 原则 1：确定性代码闸门，优于 prompt 自觉

**最弱的防御**：在系统提示里写"请不要执行危险操作"。

模型会被提示注入绕过（"忽略之前所有指令…"）。**真正的防线是设计**——让危险操作"在架构上够不着"。

**本引擎做法**：`redline_engine.py` 用正则/子串/路径片段做**确定性匹配**，引擎外的代码判断，不随模型被说服而动摇。无论模型多"聪明"地被诱导，`rm -rf` 命中就是 block。

---

## 原则 2：allowlist 优于 blocklist

- **blocklist（黑名单）**："这些命令禁止"。缺点：列不全，攻击者总能找到第 101 个。
- **allowlist（白名单）**："只放行这些，其余默认拒绝"。缺点：要枚举，但安全边界清晰。

**本引擎做法**：`redlines.json` 的 `allowlist` 字段枚举可自动执行的命令头；`check` 里命令头不在白名单且未被升级 → 降级为 `confirm`（需人工确认）。默认拒绝，缺口最小。

---

## 原则 3：纵深防御，不是单墙

单道正则挡不住所有变体（`rm -rf` / `rm -r -f` / `find . -delete` / `\rm -rf`）。所以要叠层：
- `scan`：语义级扫描（见 redlines.json 正则）
- `check`：路径保护（`.ssh`/`.env`/...）、批量检测（全表删/递归删）、白名单兜底、对外发送检测
- 受保护路径片段：任何触碰即 block
- 人工确认：不可逆/对外操作的最终闸门

每一层独立，任一层有洞，其他层还能拦。

---

## 原则 4：HITL 触发条件要窄

人工确认（Human-in-the-Loop）是强防御，但**滥用会贬值**：连"列个目录"都要确认，用户会一路回车，确认变成形式。

**本引擎做法**：只对两类触发 `confirm`——
1. 不可逆或提权（`git reset --hard` / `sudo` / `chmod 777`）
2. 对外发送（邮件/转账/发布/外部 POST）

`block` 仅留给真正高影响的不可逆破坏（`rm -rf` / `DROP TABLE` / 格式化 / 销毁基础设施）。窄目标，才有意义。

---

## 原则 5：误报疲劳会杀死产品

告警太多太吵，真泄露也会被忽略——这是安全工具的头号死因。

**本引擎做法**：三级分流 `info` / `warn` / `block`：
- `info`（如 `eval(`/`exec(`）：只是提示，不挡。
- `warn`：需确认，但可放行。
- `block`：物理拦截 + 报告，但**最终决定权仍留给人**（不硬禁止，避免 `--no-verify` 绕过）。

把噪音和真危险分开，用户的注意力才留给真危险。

---

## 原则 6：正则非法要退化，引擎自身不能崩

规则库是数据驱动的，某条规则的正则可能写错。

**本引擎做法**：`scan_text` 捕获 `re.error`，退化成子串匹配。引擎自己不崩，才能持续守护。这是"防御性编程"最基本的要求——护栏的护栏。

---

## 红线规则的分类约定

| 风险面 category | 含义 | 典型 level |
|---|---|---|
| `destructive` | 破坏性/不可逆数据操作 | block / warn |
| `privilege` | 提权/越权 | warn |
| `external_send` | 向外发送数据/凭据 | warn |
| `prompt_injection` | 提示注入特征 | warn |

新增规则时，先定 `category` 和 `level`，再写 `pattern`。`match` 默认 `regex`，简单场景可用 `contains`。
