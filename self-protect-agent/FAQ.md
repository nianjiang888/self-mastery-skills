# FAQ · self-protect-agent

## Q1：它和 guard 系列有什么区别？
`guard-*` 管"**帮用户挡外部风险**"（第三方/外部数据/外部系统，如提示注入检测、密钥泄露扫描）。
`self-protect` 管"**AI 自己别做蠢事**"——动手前的自我边界守护。一个对外，一个对内。

## Q2：block 级会真的禁止我执行吗？
不会硬禁止。它会**物理拦截 + 向你报告 + 建议确认**，但最终决定权留给人。
为什么不做硬禁止？因为会逼用户用 `--no-verify` 之类绕过，比没防线更坏。

## Q3：它能 100% 拦住提示注入吗？
不能。提示注入是 Transformer 架构级缺陷，学界共识无银弹。本引擎是纵深防御的一层，不是全能墙。
但它的"确定性代码闸门"比"在 prompt 里写别被注入"可靠得多——危险操作在架构上够不着。

## Q4：误报太多怎么办？
三级分流：`info` 只提示不挡、`warn` 需确认可放行、`block` 才物理拦截。
只对不可逆/提权/对外发送触发确认，窄目标才有意义。如果你觉得某条规则太吵，改 `resources/redlines.json` 把它的 `level` 调低即可。

## Q5：近失日志存在哪？会泄露吗？
默认在命令执行目录的 `.self-protect/near-miss-log.jsonl`。
里面只有"动作描述 + 风险面 + 规则 ID + 时间"，**不存命令的完整参数里的敏感值**（只截断前 500 字符且不含凭据值）。
要改位置用 `--store <path>`。建议把它加进 `.gitignore`。

## Q6：怎么加到我自己的 agent 工作流里？
在 agent 调用任何"写/删/发"工具之前，先跑 `python scripts/protect.py check "<命令>"`，
退出码 `4` = 停下报告，`1` = 让你确认，`0` = 放行。把这条做成 agent 的固定前置步骤即可。

## Q7：redlines.json 我能改吗？
能，而且应该。按 `references/redline-design.md` 的约定加你自己的规则：
先定 `category` 和 `level`，再写 `pattern`。`match` 默认 `regex`，简单场景用 `contains`。

## Q8：记录的近失有什么用？
海恩法则：近失是最大、最可行动的安全层。`audit` 会告诉你哪个风险面最高频、
该优先加固哪层防御。近失率上升不是退步，是系统在努力学习（Safety-II 视角）。
