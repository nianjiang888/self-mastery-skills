# 调试理论：为什么「自我调试」是真的科学，而不只是「看报错」

很多人把调试理解成"读报错、改两行、再跑"。这在小脚本上凑合，但一旦进入严肃工程，纯靠直觉的调试会迅速崩坏：你改了一处，另一处又炸；你"感觉好了"，上线又复发。本文件把 self-debug-agent 背后的硬理论讲清楚——它不是一个报错阅读器，而是一台有学术根基的**自主调试引擎**。

## 一、调试的本质：假设检验，不是瞎改

调试在认知科学里被建模为**假设-检验循环（hypothesis-driven debugging）**。你每看到一个症状，大脑其实在下意识地做一件事：

1. 观察症状（报错、错误输出、卡死）；
2. 形成假设（"可能是空指针"）；
3. 设计检验（加一个判空、跑一个用例）；
4. 根据结果修正假设或假设空间。

这个循环之所以有效，是因为它把"无限可能的错误原因"逐步收敛到一个可验证的小集合。糟糕的调试者跳过了 2→3 的检验环节，直接用"我觉得"去改，于是改动能量被浪费在大量未经证伪的猜测上。self-debug-agent 的设计铁律——**不许靠感觉定位，宣称某一行是病灶必须附覆盖率/失败证据**——正是把"假设必须可证伪"这条科学纪律焊死在工具里。

Andreas Zeller 在经典的 *Why Programs Fail*（以及更早的 FSE 1999 论文 *Yesterday, my program worked. Today, it does not. Why?*）里把这条思想工程化了：调试的核心动作是**比较一次失败执行与一次成功执行的差异**，并系统性地缩小到最小差异集。这就是下一节的 Delta Debugging。

## 二、Delta Debugging：把"为什么挂了"变成算法

Zeller 的 **Delta Debugging（DD）** 是一个二分搜索式的化简算法：给你一个"能触发失败的输入（或一组程序状态差异）"，它自动找到一个**最小的、仍能触发失败**的子集。最小，意味着噪音被去掉，真正的诱因赤裸裸地暴露出来。

为什么这重要？因为现实里的 bug 往往埋在几百行无关代码、几 MB 输入、一堆无关环境变量里。人肉去噪极慢且易错。DD 把"复现"从艺术变成可计算的搜索：从全集开始，不断剔除一半，看失败是否仍在；最终收敛到最小失败诱因。self-debug-agent 的 `--reproduce` 就是这个思想的中文落地——它不追求"复现整个系统"，而是萃取**最小失败事实**（错误类型、失败行、该行源码），让后续每一步都站在精确事实上，而不是模糊的"它有时候崩"。

> 纪律含义：**复现不了就不算 bug，更不许修**。一个拿不出最小复现的"修复"，和没修一样——你甚至没法证明它修对了。脚本遇到无错误类型的 trace 会直接拒绝进入治愈循环（退出码 2），就是这条铁律的机器化。

## 三、Self-Debugging（ICLR 2024）：让模型"自己调试自己"

2024 年，Google DeepMind 与 UC Berkeley 的 Chen 等人提出 **Self-Debugging**（*Teaching Large Language Models to Self-Debug*, ICLR 2024），这是本 Agent "自我"二字最直接的学术出处。他们的洞见是：人类程序员也很少一次写对，而是**读报错、追执行、向同事（或一只橡皮鸭）解释自己的逻辑**来暴露 bug。Self-Debugging 把这个迭代自纠过程变成了 LLM 的提示框架，核心是三步循环：

1. **Generation**：根据需求先生成一个候选程序；
2. **Explanation**：让模型用自然语言解释自己写的代码，或生成执行轨迹（逐行模拟输入怎么被处理）；
3. **Feedback**：构造反馈消息帮模型评估自己的工作——可以简单到"这段代码对吗？"，也可以是单元测试结果、或模型自己的代码解释。

关键发现：

- **橡皮鸭效应是真的**：即便没有单测，让模型解释自己的代码，它就能发现逻辑偏离需求。在 Spider（无单测的 text-to-SQL 基准）上，仅靠自我解释把整体准确率提升 2–3%，在最难档提升 **9%**。
- **想得更深胜过猜得更多**：用 self-debugging、只采样 1 个初始候选，就能匹配甚至超过采样 10×–32× 候选的基线方法。而且多数成功修复发生在 **1–3 轮**内，不需要无限迭代。
- **执行结果是锚**：有单测时（TransCoder、MBPP），self-debugging 把基线准确率提升最高 **12%**，因为它用执行结果压住了模型对自己初始错误预测的过度自信。

self-debug-agent 的 `--heal` 治愈循环就是这套三步循环的纪律版：失败 → 用证据反思根因 → 修订 → 重跑验证。脚本管记账（每轮记根因与证据），人/模型管实际补丁，但**循环结构本身强制了"解释-反馈-修订"的闭环**，而不是随机改。

补充：2025 年的 *Revisit Self-Debugging with Self-Generated Tests* 进一步把"自我调试"定义收紧——**模型不依赖人类监督、也不依赖更强模型引导，自主调试修复自己的程序**。它还区分了 post-execution（跑完看输出对不对）与 in-execution（分析执行中间状态）两种范式，并指出后者能减少"自生成测试的偏差"。这恰恰印证了 self-debug 的「自我」本质：不假外求。

## 四、频谱故障定位 SBFL：让"感觉是这儿"变成数字

假设检验需要把"可疑代码"排个序。人靠直觉排，容易受最近改过的代码、最显眼的代码干扰。**频谱故障定位（Spectrum-Based Fault Localization, SBFL）** 用测试覆盖数据客观排序：

- 统计每行代码被**通过测试**覆盖多少次（passed）、被**失败测试**覆盖多少次（failed）；
- 直觉是：**失败测试覆盖多、通过测试覆盖少**的行，更可能是病根。

两个经典公式：

- **Tarantula**（Jones & Harrold, 2002）：可疑度 = (失败覆盖占比) / (失败覆盖占比 + 通过覆盖占比)。用颜色深浅可视化可疑行。
- **Ochiai**（Abreu et al., 2007）：可疑度 = 失败覆盖 / √(失败测试总数 × (失败覆盖 + 通过覆盖))。大量实证表明 Ochiai 稳定优于 Tarantula。

self-debug-agent 的 `scripts/localize.py` 就是把这两套公式实现出来：给它一个 spectrum（每行 passed/failed），它排出 Top-N 可疑行，并标注最可能病灶。这是元认知在调试里的投影——**不是"我感觉是这一行"，而是"数据说最可能是这一行"**。`--classify` 则先用 `bug_taxonomy.json` 的签名探针把 bug 归到六类，给出根因与修法方向，再交给 localize 锁死行号。

## 五、把四块拼起来

| 理论 | 出处 | 在本 Agent 的落点 |
|---|---|---|
| 假设-检验调试 | 认知科学 / Zeller | 铁律：宣称病灶必须附证据 |
| Delta Debugging | Zeller, FSE 1999 | `--reproduce` 萃取最小失败事实 |
| Self-Debugging 三步循环 | Chen et al., ICLR 2024 | `--heal` 治愈循环（解释-反馈-修订）|
| SBFL（Tarantula/Ochiai）| Jones&Harrold 2002 / Abreu 2007 | `localize.py` 可疑度排序 |

这四块共同保证：self-debug-agent 不是"又一个报错阅读器"，而是一台**有理论打底、有纪律约束、有数字支撑**的自主调试引擎。它和 self-evaluate-agent 同源（都是 Reflexion 式的"产出→评估→反思→改进"），只是这里被评估和改进的对象是**正确性**而非**质量**。

## 六、给使用者的提醒

理论很强，但边界要清楚（详见 SKILL.md 的红线）：

- SBFL 是**排序**不是**定罪**：可疑度高的行要人工确认，别无脑改 Top1；
- Self-Debugging 的效果受限于模型本身的代码理解力——它解释不清自己代码时，就定位不到偏差；
- 把每个 bug 落成永久回归测试（`--regress`），才是让理论真正产生"复利"的动作。
