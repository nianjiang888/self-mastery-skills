# 问责机制与违约判定方法论

self-discipline-agent 的核心不是「记一条决心」，而是「让承诺可被核查、让违约可见」。本文说明 `audit` / `report` 背后的方法与算法。

## 一、为什么需要外部问责，而不是自我提醒

自我提醒依赖「未来的自己记得并执行」，而承诺装置依赖「机制自动触发后果」。前者失败率极高（见理论篇自我损耗争议）。因此引擎把问责外置：违约由**客观截止时间 + 打卡缺失**自动判定，不由用户主观「我觉得我做到了」决定。

## 二、数据结构（事件溯源）

所有记录写入单一 `discipline-log.jsonl`，两类事件：

```
{type:"commit", id, ts, content, deadline, stake, partner, category}
{type:"checkin", id, ts}
```

采用 append-only 事件流而非可变状态，保证：
- 可重跑：任意时刻重跑 `audit`/`report` 都从同一份事实得到一致结论；
- 可审计：每次打卡、每条承诺都有时间戳留痕，无法事后篡改叙事。

## 三、状态判定算法

对每条 commit，综合其 deadline 与对应 checkin 时间戳判定状态：

```
if 有 checkin:
    if 无 deadline: status = kept
    elif 存在 deadline 前(含当日)的 checkin: status = kept
    else: status = breached
else:
    if 无 deadline: status = open      # 仍开放，未到期也未违约
    elif deadline < 当前时间: status = breached
    else: status = open
```

关键点：**「履约」以打卡发生在期限前为准**。过期后才补打卡，仍记为违约——这避免「事后补卡洗白」破坏问责严肃性。

## 四、违约聚类的意义

`audit` 不做笼统的「你违约了 N 次」，而是**按类别聚合**：

- 同类承诺反复违约 → 说明该类靠当前机制无效，需升级装置（加押金/换监督人/改 if-then）；
- 暴露「最易破的承诺类型」→ 把有限精力放在改造高频失败域。

这是把零散失败变成**可行动情报**，而非单纯制造愧疚。

## 五、退出码设计

| 情形 | 退出码 | 含义 |
|---|---|---|
| 无违约 | `0` | 正常 |
| 有违约但非系统性 | `1` | 需关注，提示检查薄弱类型 |
| 某类别 ≥2 条且全部违约，或总履约率 <30% | `4` | 系统性失守警报 |

`4` 是刻意设置的「双环级」信号：它告诉你问题不在某一次失误，而在**该类承诺的设计本身**——该换机制了，而不是「下次注意」。

## 六、降低误报与疲劳

- **到期前打卡即履约**：不因「差一点」误判违约。
- **无期限承诺不强制违约**：未设 deadline 的开放承诺只记 `open`，不拖累履约率。
- **可解释**：每条违约都列出 id / 类别 / 内容 / 期限，使用者可复核。
- **类别自动识别**：从内容匹配健康/工作/财务/情绪/习惯，降低登记负担；也支持显式 `--category` 覆盖。

## 七、局限与诚实边界

- 打卡是「自报」行为，引擎不验证你**真的**做了——这是机制的可解释代价。重要承诺建议配合 `--partner` 让监督人交叉验证。
- 类别识别靠关键词，生僻表达可能归为「未分类」；用 `--category` 补即可。
- 履约率随样本增多才可信；一两条记录下的百分比意义有限。
